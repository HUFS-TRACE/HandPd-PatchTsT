## 1. ⚠️ 음성 subject_id — 같은 사람이 두 개의 id를 갖는다

### 무엇이 잘못됐나

원본에서 아래 두 파일은 **같은 사람(34번)** 이다.

```
HC_A1_0034.npy       모음 '아'
HC_PATAKA_0034.npy   파타카(DDK)
```

그런데 `npy_to_npz.py`가 폴더별로 돌며 파일명 맨 앞 숫자를 subject_id로 쓰는 바람에,
모음은 `전처리_data3_npz`(id 82~192), 파타카는 `전처리_data4_npz`(id 234~334)로 들어가
한 사람이 서로 다른 두 id를 받았다.

| 수집분 | npz id 범위 | 인원 |
|---|---|---|
| 전처리_data1_npz | 1~81 | 81 |
| 전처리_data3_npz (모음) | 82~192 | 111 (HC 58 / PD 53) |
| 전처리_data2_npz | 193~233 | 41 |
| 전처리_data4_npz (파타카) | 234~334 | 101 (HC 50 / PD 51) |

**모음 111명과 파타카 101명 중 99명이 동일 인물이다.**

### 왜 문제인가

`StratifiedGroupKFold(groups=subject_id)`는 id를 사람이라고 믿고 자른다. 한 사람이 두 id로
갈려 있으면 한 조각은 train, 다른 조각은 test로 갈 수 있고(5-fold면 약 80% 확률), 그러면
학습 때 들은 목소리를 test에서 다시 듣는다. 같은 사람·같은 마이크·같은 세션이라 정확도가
실제보다 높게 나오고, 그 숫자로 "공유 인코더가 도움이 되는가"를 판정하면 판정이 오염된다.

NewHandPD에서 `subject_id = Person_ID_Number`로 바꿔 P1=P4 중복을 잡았던 것과 같은 유형이다.
필기는 4명 규모였고 이번은 99명이다.

### 근거 — 순서 추론이 아니다

"같은 번호 = 같은 사람"의 근거는 두 가지다.

1. `parkinson-audio-preprocessing/README.md`의 명시 — *"파일명 맨뒤 숫자가 같은번호면
   같은 사람입니다. 전처리_data3와 pataka 데이터 해당"*
2. **번호가 성기고 불규칙한데도 집합이 겹친다.** 두 수집분이 각자 1,2,3…으로 번호를
   매겼다면 파타카는 1~101이 촘촘히 찼어야 하는데, 실제로는 모음과 똑같이 듬성듬성하다.

```
PD 번호: 4, 6, 7, 8, 9, 10, ..., 58, 66, 67, 70, 77, 78, 79, 108, 109, 111, 113, 115, 117
HC 번호: 34, 36, 45, 48, 49, 51, ..., 105, 112, 116, 118, 120, ..., 145
```

같은 범위에서 번호를 무작위로 다시 뽑으면 교집합이 평균 33.2명(최대 47명)이다.
실제 99명은 우연으로 설명되지 않는다.

> **다만 직접 증거는 아니다.** `HC_A1_0034`와 `HC_PATAKA_0034`가 실제로 같은 사람인지
> 음성으로 확인한 것은 아니고, 원본 코퍼스가 클래스별 단일 번호 체계를 썼다는 전제를
> 신뢰하는 것이다.

### 사람 식별 키는 (클래스, 번호)다 — 번호만 쓰면 안 된다

번호만으로 묶었다가 **audio의 HC 68과 pataka의 PD 68을 한 사람으로 합치는 실수**를 했다.
스크립트의 라벨 충돌 검사가 걸러내서 저장을 거부했고, 키를 `(클래스, 번호)`로 고쳤다.
README가 HC 명단과 PD 명단을 따로 나열한 것이 그 뜻이었다. 병합 대상이 101 → **99명**으로 줄었다.

### 조치

`Shared-Parkinson/fix_subject_id.py` — 원본 파일명에서 대응을 세우고 **파일 수·클래스로
검산**한 뒤 `voice_subject_id_map.json`을 내보낸다. 검산이 하나라도 어긋나면 매핑을 만들지
않는다(잘못 합치는 것이 안 합치는 것보다 나쁘다).

```
정정 전 subject_id : 334개
정정 후 실제 사람  : 235명   (99명이 두 id로 갈려 있었음)
라벨 충돌 0건
사람당 파일 수: 최소 1 / 중앙 9 / 최대 14
5-fold 기준 fold당 test ≈ 47명 → 1명 ≈ 2.1%p
```

데이터 파일은 건드리지 않았다. npz 1,658개를 고쳐쓰는 대신 매핑표만 내보내고,
윈도잉 단계(#2)에서 `canonical_subject_id()`로 적용한다. 되돌릴 수 있게 두려는 것이다.

> 참고로 실제 사람이 235명이면 **1명 ≈ 2.1%p**로, 필기(61명, fold당 12명, 1명 8.3%p)보다
> 훨씬 안정적이다. `depth_ee_findings.md` §2-6이 지적한 "피험자 정확도를 지표로 쓸 수 없다"
> 문제가 음성에서는 상당히 완화된다.

### ❓ 미해결 — 68·69번

```
번호 68:  HC_A1, HC_A2, HC_E2, HC_I1, HC_I2, HC_O1, HC_O2, HC_U1  (모음 8개, 전부 HC)
          PD_PATAKA_0068                                           (파타카 1개, PD)
번호 69:  동일 패턴
```

같은 번호인데 모음은 HC, 파타카는 PD다. 나머지 99명은 클래스까지 전부 일치하는데 이 둘만
어긋나고, 68·69는 README의 HC 명단·PD 명단 **어느 쪽에도 없다**.

| 해석 | 결과 |
|---|---|
| (a) 진짜 다른 사람 (번호 겹침) | 지금 처리 그대로. 실제 사람 235명 |
| (b) 파타카 파일의 클래스 오타 | HC로 고치고 병합. 실제 사람 233명 |

`전처리_audio` 안에서는 같은 번호가 HC·PD에 동시에 쓰인 적이 한 번도 없어(111명 중 0건)
번호가 전역 식별자처럼 동작한다. 그렇다면 (b)가 더 그럴듯하다.

**→ 원본 받은 곳에서 68·69번 확인 필요.** 235명 중 2명 차이라 후속 작업을 막을 정도는 아니며,
(b)로 밝혀지면 `voice_subject_id_map.json`에 두 줄 추가하면 된다.

## 2. ⚠️ 음성이 가변 길이 — 아직 모델에 못 물린다

```
npz 1,658개 = 파일 하나당 샘플 하나
X shape: (80, T)   T = 54 ~ 3476  (중앙 438)
10ms hop 기준 → 0.5초 ~ 34.8초
라벨: 정상 812 / 환자 846 (파일 기준)
```

`shared_dataset.load_modality`는 `X[N, 80, T]` 한 덩어리에 **T가 고정**이어야 한다.
PatchTST가 `num_patches = (T - patch_len) / stride + 1`로 토큰 수를 정하고, 그 값으로
위치 인코딩 크기와 head의 `Linear(C*d_model, 2)`가 결정되기 때문이다. 길이가 다르면
한 배치로 스택하는 것 자체가 안 된다.

**필요한 것**: `preprocess.py`가 필기에 하는 것과 같은 고정 길이 슬라이딩 윈도우(50% 겹침).
필기가 2초/1000Hz = 2000샘플이니, 음성은 10ms hop 기준 2초 = 200프레임이 대응된다.

같이 챙길 것:

- **`canonical_subject_id()` 적용을 윈도잉 직전에** — 그래야 fold가 사람 단위로 걸린다 (#1)
- **긴 녹음 과표현** — 34.8초짜리는 0.5초짜리보다 윈도우가 70배 나온다. 필기에서
  `MAX_WIN_PER_SUBJECT`로 완화했던 문제
- **모음/파타카 분리** — README가 *"모음과 DDK는 평가하는 발성 기관이 완전히 달라
  섞어 학습시키면 안 된다"* 고 명시. 윈도우마다 `task` 태그 유지 필요

## 4. `task` 필드가 모음 종류를 잃었다

```
task 분포:  'a' 1,557개  /  'pataka' 101개
```

그런데 `전처리_audio` 원본은 **A·E·I·O·U 전부**다(`HC_A1`, `HC_E2`, `HC_I1`, `HC_O3`, `HC_U1`…).
`npy_to_npz.py`가 `task = np.array("a")`로 하드코딩해서("이번 폴더는 모두 모음 a") 구분이 사라졌다.

파일명 접미사(`-01`~`-13`)로도 복원할 수 없다. 사람마다 보유 파일 구성이 달라서다 —
0034번은 A1, A2, E2, I1, I2, O1, O2, U1 순이라 E1이 없고, E1이 있는 사람은 같은 접미사가
다른 모음을 가리킨다. 접미사는 사람별 일련번호일 뿐이다.

모음↔파타카 구분은 `task`로 되지만 **모음 종류는 npz만으로 복원 불가**다.
필요하면 원본 npy 파일명에서 다시 만들어야 한다.

## 5. 음성 기준선 부재

`2모달 Early Exit` 노트(Notion, 2026-08-04)가 지적한 항목이 그대로 남아 있다.

| | 필기 | 음성 |
|---|---|---|
| 결과 CSV | 수십 개 | **0** |
| seed 반복 | 3~4 | **1** |
| 통계 검정 | t값 판정 | **없음** |
| 통제 대조군 | E1 12회 | **없음** |

기존 음성 75.0%는 단일 seed 결과이고 결과 파일도 남지 않았다. 필기에서 배운 대로
**seed만 바꿔도 5.8%p, 최대 11.5%p** 흔들린다.

> **공유 인코더를 만들어도 비교할 기준선이 없으면 결과 해석이 안 된다.**

또한 공정 비교를 위해 **단독 모델도 공유 모델과 같은 설정(d64/L6)으로 다시 돌려야** 한다.
필기 최적은 d64/L6, 음성 최적은 d128/L2로 서로 달라서, 그냥 비교하면 "공유 효과"와
"설정 효과"가 섞인다.

```
✅ 공유(d64 L6) vs 단독(d64 L6)      ← 설정 같음 → 공유 효과만 보임
❌ 공유(d64 L6) vs 단독(d128 L2)     ← 해석 불가
```

## 6. 공유 파라미터 비율이 설계 문서와 다르다

| | 이 구현 | 설계 문서(Notion) |
|---|---|---|
| 공유 인코더 | 200,832 (**92.1%**) | 200,832 (**75.6%**) |
| 필기 전용 | 7,246 | 13,580 |
| 음성 전용 | 9,922 | 51,340 |

**공유 인코더 수치는 소수점까지 일치**한다(d64 · 6층 · d_ff 128). 차이는 모달 전용 쪽이다.

이 구현은 `model.py`와 맞추려고 sinusoidal 위치 인코딩(파라미터 0)을 썼는데, 문서 수치는
학습형 PE를 가정한 것으로 보인다. 다만 학습형 PE를 넣어도 음성 51,340은 재현되지 않아
(계산상 1만 근처) **문서 쪽 수치의 근거 확인이 필요**하다.

공유 비율이 높은 것 자체는 "인코더를 공유했다"는 주장에 유리하다.

## 다음 단계

```
1. 음성 subject_id 정정 적용        ← fix_subject_id.py 작성 완료, 윈도잉에서 적용
2. 음성 고정 윈도잉 → voice_windows.npz
3. 음성 단독 기준선 (d64/L6, seed 3개, CSV 저장)
4. 필기 단독 기준선 재실행 (d64/L6로 통일)
5. 공유 인코더 학습 → 3·4와 비교
```

1·2가 끝나기 전에는 3 이후를 할 수 없고, 3·4가 없으면 5의 숫자를 해석할 수 없다.

병렬로 가능한 것: torch 실행 환경 확보(#3) — 합성 데이터 스모크 테스트는 실데이터와 무관하다.

> Early Exit은 아직 붙이지 않았다. 깊이 축은 `depth_ee_findings.md`에서 작동하지 않음이
> 확정됐고(정적 L1 ≈ L6, t=0.51), 현재 우선순위는 시간 축(`paper/exp2_protocol.md`)이다.

## A-1. 병합 키를 `번호` → `(클래스, 번호)` 로 고침 ⭐

**처음 한 것** — 원본 파일명 맨 뒤 숫자만으로 사람을 식별해 data4를 data3에 합쳤다.
정렬 대응 검산(파일 수·라벨)이 111/111, 101/101로 전부 통과해서 맞다고 봤다.

**증상** — 사후 검증에서 라벨 충돌 2건이 떴다.

```
정정 후 실제 사람  : 233명
한 사람이 두 라벨을 갖는 경우: 2건 ❌ [143, 144]
→ 라벨 충돌. 매핑이 틀렸다는 뜻이므로 저장하지 않는다.
```

**원인** — `전처리_audio`의 **HC 68**과 `전처리_pataka`의 **PD 68**을 한 사람으로 합쳤다.
번호는 코퍼스 전역이 아니라 **클래스 안에서만 유일**하다. README가 HC 명단과 PD 명단을
따로 나열한 것이 그 뜻이었는데, 번호만 보고 놓쳤다.

정렬 검산이 통과한 이유도 이걸로 설명된다 — 각 수집분 **안에서는** 번호가 클래스에 걸쳐
겹치지 않아(111명 중 0건) 번호 오름차순이 사람을 유일하게 정한다. 문제는 수집분을
**가로질러** 합칠 때만 드러난다.

**고친 것** — 사람 키를 `(클래스, 번호)` 쌍으로 바꿨다. 병합 대상이 101 → **99명**으로 줄고
라벨 충돌이 0건이 됐다. 아울러 "이 수집분 안에서 번호가 HC·PD에 겹치는가"를 먼저 확인하는
가드를 넣어, 정렬 가설이 성립하지 않는 데이터가 들어오면 즉시 멈추게 했다.

**남긴 교훈** — 이 오류를 잡은 건 사후 검증(라벨 충돌 검사)이었다. 그게 없었으면 잘못된
매핑이 그대로 저장되고, 두 사람이 한 사람으로 합쳐진 채 fold가 갈렸을 것이다.
**"검산이 어긋나면 저장하지 않는다"는 가드를 먼저 짜고 매핑을 만든 것이 유효했다.**

## A-2. 데이터 파일을 고치지 않고 매핑표만 내보낸 이유

| | npz 직접 수정 | **매핑표(JSON) 방식** |

| 되돌리기 | 어려움 (1,658개 재생성) | 파일 하나 지우면 끝 |
| 리뷰 | 바이너리 diff | 텍스트 diff |

| 68·69 결론 바뀌면 | 전체 재변환 | **두 줄 수정** |

아직 확정 안 된 질문(68·69)이 남아 있는 상태에서 원본을 덮어쓰는 건 이르다고 봤다.
윈도잉 단계에서 `canonical_subject_id()`로 적용하면 결과는 같으면서 되돌릴 수 있다.

## A-3. 두 모달 손실을 합산해 backward를 **한 번만** 호출

**문제** — Notion 「2모달 Early Exit」 §3-1이 지적한 교란 셋 중 하나가
*"인코더 업데이트 횟수 약 2배(배치를 번갈아 돌림)"* 였다. 공유 모델이 더 좋게 나와도
그게 지식 전이 때문인지 그냥 더 많이 업데이트해서인지 구분되지 않는다.

**고친 것** — 모달을 번갈아 backward 하지 않고 한 스텝에서 두 손실을 **합산한 뒤
backward를 한 번만** 호출한다.

```python
loss = criteria["hw"](model(x_hw, "hw"), y_hw) \
     + criteria["voice"](model(x_voice, "voice"), y_voice)
loss.backward()      # 두 기울기가 같은 인코더로 함께 흘러들어감
optimizer.step()     # 스텝은 1회
```

**결과** — epoch당 옵티마이저 스텝 수가 필기 단독 학습과 **같아진다**(둘 다 152스텝).
교란 3개 중 하나가 구조적으로 제거됐다. 남은 둘(데이터량 증가, 이질 분포 혼합)은 여전히
대조군이 필요하다.

## A-4. 로더 길이 불일치 — `longest` 를 기본으로

필기 13,474 vs 음성 2,008 윈도우로 6.7배 차이가 난다.

| | zip (shortest) | **longest (기본)** |
|---|---|---|
| 필기 데이터 | 매 epoch **85% 버림** | 전부 사용 |
| 음성 데이터 | 전부 사용 | 약 6.7회 반복 노출 |
| 단독 기준선과 비교 | **깨짐** (학습 데이터가 다름) | 성립 |

필기 85%를 버리면 "공유 vs 단독" 비교에서 학습 데이터량이 달라져 §5의 공정 비교 조건이
무너진다. 그래서 `longest`를 골랐다. 대가는 음성 과적합이 빨라지는 것이고,
`--pair-mode shortest`로 바꿔 확인할 수 있게 남겼다.

## A-5. 위치 인코딩을 sinusoidal로 유지 (설계 문서와 다름)

설계 문서의 파라미터 수치(모달 전용 13,580 / 51,340)는 **학습형 PE**를 가정한 것으로 보인다.
그래도 `model.py`와 동일한 **sinusoidal**(파라미터 0)을 유지했다.

**이유** — 이 모델의 존재 이유가 "같은 설정 단독 모델과 비교해 공유 효과만 분리하는 것"이다.
백본 구성이 하나라도 다르면 §5에서 지적한 것처럼 "공유 탓인지 설정 탓인지" 섞인다.
`model.py`의 `PatchTSTClassifier`와 RevIN·PE·pre-LN·GELU·channel-independent 패칭을
전부 일치시키는 쪽을 택했다.

**부수 효과** — 공유 비율이 문서(75.6%)보다 높은 **92.1%**가 됐다. "인코더를 공유했다"는
주장에는 유리하지만, 문서 수치와 어긋나므로 §6에 확인 사항으로 남겼다.

## A-6. 조기중단을 모달 val loss의 **합**으로

인코더가 하나뿐이라 모달별로 다른 시점에 멈출 수가 없다. 합으로 걸면 한 모달이 먼저
과적합해도 다른 쪽이 내려가는 동안 합이 계속 줄어 멈추지 않는다.

**구조적 타협임을 인정하고**, 대신 모달별 val loss를 따로 기록해 눈으로 확인할 수 있게 했다.
"공유 모델은 조기중단 시점이 단독과 다를 수 있다"는 점은 §5 비교에서 감안해야 한다.

## A-7. 모달별 클래스 가중치를 따로 계산

필기(1:1.77)와 음성(1:1.04)은 불균형 정도가 다르다. 한쪽 비율로 양쪽을 덮으면 다른 모달의
손실이 왜곡되므로, fold별 train 분포에서 각각 역빈도로 계산한다.
분모에 클래스 수를 두어 가중치 평균이 1.0이 되게 했다 — 손실 스케일이 유지되어
learning rate를 다시 잡을 필요가 없다.

## A-8. 검증 범위를 정직하게 표기

torch를 못 돌리는 환경이라 "학습이 돌아간다"를 확인할 수 없었다. 그래서 확인한 것과
못 한 것을 §3에 나눠 적었고, 커밋 메시지에도 남겼다. 돌려보지 않은 코드를
"동작 확인됨"으로 적으면 나중에 그 표기를 믿고 넘어가게 된다.

numpy로 검산 가능한 부분(텐서 shape 수식, 파라미터 수)은 실제로 재현해서 확인했고,
공유 인코더 파라미터가 설계 문서의 200,832와 소수점까지 일치하는 것까지는 확인했다.
