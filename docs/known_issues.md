## 1. ⚠️ 음성 subject_id — 같은 사람이 두 개의 id를 갖는다

### 무엇이 잘못됐나

원본에서 아래 두 파일은 **같은 사람(34번)** 이다.

```
HC_A1_0034.npy       모음 '아'
HC_PATAKA_0034.npy   파타카(DDK)
```

그런데 `npy_to_npz.py`가 폴더별로 돌며 파일명 맨 앞 숫자를 subject_id로 쓰는 바람에,
모음은 `전처리_data3_npz`(id 82~192), 파타카는 `전처리_data4_npz`(id 234~334)로 들어가
한 사람이 서로 다른 두 id를 받았다.

| 수집분 | npz id 범위 | 인원 |
|---|---|---|
| 전처리_data1_npz | 1~81 | 81 |
| 전처리_data3_npz (모음) | 82~192 | 111 (HC 58 / PD 53) |
| 전처리_data2_npz | 193~233 | 41 |
| 전처리_data4_npz (파타카) | 234~334 | 101 (HC 50 / PD 51) |

**모음 111명과 파타카 101명 중 99명이 동일 인물이다.**

### 왜 문제인가

`StratifiedGroupKFold(groups=subject_id)`는 id를 사람이라고 믿고 자른다. 한 사람이 두 id로
갈려 있으면 한 조각은 train, 다른 조각은 test로 갈 수 있고(5-fold면 약 80% 확률), 그러면
학습 때 들은 목소리를 test에서 다시 듣는다. 같은 사람·같은 마이크·같은 세션이라 정확도가
실제보다 높게 나오고, 그 숫자로 "공유 인코더가 도움이 되는가"를 판정하면 판정이 오염된다.

NewHandPD에서 `subject_id = Person_ID_Number`로 바꿔 P1=P4 중복을 잡았던 것과 같은 유형이다.
필기는 4명 규모였고 이번은 99명이다.

### 근거 — 순서 추론이 아니다

"같은 번호 = 같은 사람"의 근거는 두 가지다.

1. `parkinson-audio-preprocessing/README.md`의 명시 — *"파일명 맨뒤 숫자가 같은번호면
   같은 사람입니다. 전처리_data3와 pataka 데이터 해당"*
2. **번호가 성기고 불규칙한데도 집합이 겹친다.** 두 수집분이 각자 1,2,3…으로 번호를
   매겼다면 파타카는 1~101이 촘촘히 찼어야 하는데, 실제로는 모음과 똑같이 듬성듬성하다.

```
PD 번호: 4, 6, 7, 8, 9, 10, ..., 58, 66, 67, 70, 77, 78, 79, 108, 109, 111, 113, 115, 117
HC 번호: 34, 36, 45, 48, 49, 51, ..., 105, 112, 116, 118, 120, ..., 145
```

같은 범위에서 번호를 무작위로 다시 뽑으면 교집합이 평균 33.2명(최대 47명)이다.
실제 99명은 우연으로 설명되지 않는다.

> **다만 직접 증거는 아니다.** `HC_A1_0034`와 `HC_PATAKA_0034`가 실제로 같은 사람인지
> 음성으로 확인한 것은 아니고, 원본 코퍼스가 클래스별 단일 번호 체계를 썼다는 전제를
> 신뢰하는 것이다.

### 사람 식별 키는 (클래스, 번호)다 — 번호만 쓰면 안 된다

번호만으로 묶었다가 **audio의 HC 68과 pataka의 PD 68을 한 사람으로 합치는 실수**를 했다.
스크립트의 라벨 충돌 검사가 걸러내서 저장을 거부했고, 키를 `(클래스, 번호)`로 고쳤다.
README가 HC 명단과 PD 명단을 따로 나열한 것이 그 뜻이었다. 병합 대상이 101 → **99명**으로 줄었다.

### 조치

`Shared-Parkinson/fix_subject_id.py` — 원본 파일명에서 대응을 세우고 **파일 수·클래스로
검산**한 뒤 `voice_subject_id_map.json`을 내보낸다. 검산이 하나라도 어긋나면 매핑을 만들지
않는다(잘못 합치는 것이 안 합치는 것보다 나쁘다).

```
정정 전 subject_id : 334개
정정 후 실제 사람  : 235명   (99명이 두 id로 갈려 있었음)
라벨 충돌 0건
사람당 파일 수: 최소 1 / 중앙 9 / 최대 14
5-fold 기준 fold당 test ≈ 47명 → 1명 ≈ 2.1%p
```

데이터 파일은 건드리지 않았다. npz 1,658개를 고쳐쓰는 대신 매핑표만 내보내고,
윈도잉 단계(#2)에서 `canonical_subject_id()`로 적용한다. 되돌릴 수 있게 두려는 것이다.

> 참고로 실제 사람이 235명이면 **1명 ≈ 2.1%p**로, 필기(61명, fold당 12명, 1명 8.3%p)보다
> 훨씬 안정적이다. `depth_ee_findings.md` §2-6이 지적한 "피험자 정확도를 지표로 쓸 수 없다"
> 문제가 음성에서는 상당히 완화된다.

### ❓ 미해결 — 68·69번

```
번호 68:  HC_A1, HC_A2, HC_E2, HC_I1, HC_I2, HC_O1, HC_O2, HC_U1  (모음 8개, 전부 HC)
          PD_PATAKA_0068                                           (파타카 1개, PD)
번호 69:  동일 패턴
```

같은 번호인데 모음은 HC, 파타카는 PD다. 나머지 99명은 클래스까지 전부 일치하는데 이 둘만
어긋나고, 68·69는 README의 HC 명단·PD 명단 **어느 쪽에도 없다**.

| 해석 | 결과 |
|---|---|
| (a) 진짜 다른 사람 (번호 겹침) | 지금 처리 그대로. 실제 사람 235명 |
| (b) 파타카 파일의 클래스 오타 | HC로 고치고 병합. 실제 사람 233명 |

`전처리_audio` 안에서는 같은 번호가 HC·PD에 동시에 쓰인 적이 한 번도 없어(111명 중 0건)
번호가 전역 식별자처럼 동작한다. 그렇다면 (b)가 더 그럴듯하다.

**→ 원본 받은 곳에서 68·69번 확인 필요.** 235명 중 2명 차이라 후속 작업을 막을 정도는 아니며,
(b)로 밝혀지면 `voice_subject_id_map.json`에 두 줄 추가하면 된다.

## 2. ✅ 음성이 가변 길이 — 해소됨

> **2026-08-07 해소.** `Shared-Parkinson/make_voice_windows.py`로 2초(200프레임) ·
> 50% 겹침 윈도잉 완료. 산출물은 Google Drive `학술제/data/voice_windows_2s.npz`
> (388 MB). LFS 용량(이미 1.17 GB)을 더 늘리지 않으려고 저장소에는 올리지 않았다.
>
> ```
> X (7658, 80, 200) float32   정상 3815 / 환자 3843  (1:1.01)
> 원본 1,658 파일 → 세그먼트 7,658개 (200프레임 미만 43개는 -80dB 패딩)
> 화자 235명 · 한 화자 두 라벨 0건 · 파타카 99명이 모음 화자로 병합 확인
> 화자당 세그먼트 최소 1 / 중앙 28 / 최대 227 · 세그먼트 1개뿐인 화자 37명
> ```
>
> 클래스 균형이 **1:1.01**로 거의 완벽하다(필기는 1:1.77). 화자가 235명이라
> fold당 test ≈ 47명, **1명 ≈ 2.1%p**로 필기(12명, 8.3%p)보다 4배 안정적이다.
>
> 남은 것: 긴 녹음 과표현(최대/중앙 8.1배)은 상한을 걸지 않았고, 모음/파타카는
> `task`로 구분만 해두고 분리 학습은 하지 않았다.

<details><summary>당시 문제 기술 (기록용)</summary>

```
npz 1,658개 = 파일 하나당 샘플 하나
X shape: (80, T)   T = 54 ~ 3476  (중앙 438)
10ms hop 기준 → 0.5초 ~ 34.8초
라벨: 정상 812 / 환자 846 (파일 기준)
```

`shared_dataset.load_modality`는 `X[N, 80, T]` 한 덩어리에 **T가 고정**이어야 한다.
PatchTST가 `num_patches = (T - patch_len) / stride + 1`로 토큰 수를 정하고, 그 값으로
위치 인코딩 크기와 head의 `Linear(C*d_model, 2)`가 결정되기 때문이다. 길이가 다르면
한 배치로 스택하는 것 자체가 안 된다.

**필요한 것**: `preprocess.py`가 필기에 하는 것과 같은 고정 길이 슬라이딩 윈도우(50% 겹침).
필기가 2초/1000Hz = 2000샘플이니, 음성은 10ms hop 기준 2초 = 200프레임이 대응된다.

같이 챙길 것:

- **`canonical_subject_id()` 적용을 윈도잉 직전에** — 그래야 fold가 사람 단위로 걸린다 (#1)
- **긴 녹음 과표현** — 34.8초짜리는 0.5초짜리보다 윈도우가 70배 나온다. 필기에서
  `MAX_WIN_PER_SUBJECT`로 완화했던 문제
- **모음/파타카 분리** — README가 *"모음과 DDK는 평가하는 발성 기관이 완전히 달라
  섞어 학습시키면 안 된다"* 고 명시. 윈도우마다 `task` 태그 유지 필요

</details>

## 3. ✅ 공유 인코더 실학습 미검증 — 해소됨

> **2026-08-07 해소.** 작업 PC에 MSVC 재배포 패키지가 없어 torch가 로드되지 않았는데,
> **시스템 설치 없이** 우회했다 — `pip install msvc-runtime`으로 DLL을 venv에 받고,
> `sitecustomize.py`에서 `os.add_dll_directory()`로 경로를 추가했다. 관리자 권한이
> 필요 없고 그 venv 안에서만 유효하다.
>
> ```
> torch 2.13.0+cpu   forward OK
> ```
>
> 스모크 테스트(합성 데이터, 3-fold) → 두 모달 모두 정확도 1.000으로 학습 확인.
> 이어서 실데이터 5-fold를 CPU로 완주했다(§7).

### ⚠️ 그 과정에서 잡은 버그 — 합성 데이터가 층화 없이 갈렸다

첫 스모크 테스트에서 정확도가 **정확히 0.000**, AUC `nan`이 나왔다.

```
fold 0: train [72, 0]  test [0, 80]    ← train 전부 정상, test 전부 환자
fold 1: train [0, 72]  test [80, 0]    ← 정반대
```

`synthetic()`이 `label = s % 2`로 라벨을 매겼는데 `GroupKFold`가 층화를 하지 않아
홀/짝 피험자를 그대로 fold로 갈라버렸다. 학습에서 test 클래스를 한 번도 못 보니
정확도가 0이 된다. 라벨을 `rng.shuffle`로 섞도록 고쳤다.

> **README §7의 "GroupKFold는 층화를 하지 않는다"가 실제로 터진 사례다.**
> 실데이터(61명·235명)에서는 이렇게까지 극단적으로 갈리지 않지만, **fold별 클래스
> 비율은 한 번 찍어봐야 한다.** 특히 필기는 fold당 12명이라 위험하다.

## 4. `task` 필드가 모음 종류를 잃었다

```
task 분포:  'a' 1,557개  /  'pataka' 101개
```

그런데 `전처리_audio` 원본은 **A·E·I·O·U 전부**다(`HC_A1`, `HC_E2`, `HC_I1`, `HC_O3`, `HC_U1`…).
`npy_to_npz.py`가 `task = np.array("a")`로 하드코딩해서("이번 폴더는 모두 모음 a") 구분이 사라졌다.

파일명 접미사(`-01`~`-13`)로도 복원할 수 없다. 사람마다 보유 파일 구성이 달라서다 —
0034번은 A1, A2, E2, I1, I2, O1, O2, U1 순이라 E1이 없고, E1이 있는 사람은 같은 접미사가
다른 모음을 가리킨다. 접미사는 사람별 일련번호일 뿐이다.

모음↔파타카 구분은 `task`로 되지만 **모음 종류는 npz만으로 복원 불가**다.
필요하면 원본 npy 파일명에서 다시 만들어야 한다.

## 5. ⚠️ 기준선 — 단독은 조건 일치로 확보, 공유 쪽 seed가 1개

`2모달 Early Exit` 노트(Notion, 2026-08-04)가 지적한 항목의 **일부만** 채워졌다.

| | 필기 | 음성 |
|---|---|---|
| d64/L6 단독 기준선 | ✅ `pareto_size_d64L6_2s{,_s1,_s7}.csv` | ✅ `voice_baseline_d64L6_s42.csv` |
| **seed 반복** | **3개 (42·1·7)** | **1개 (42만)** |
| 통계 검정 | 가능 | 표본 부족으로 불가 |
| 통제 대조군 | E1 12회 | 없음 |

기존 음성 75.0%는 단일 seed였고 결과 파일도 없었다. 이번에 **정정된 화자 ID·전체
데이터·통일 설정**으로 다시 잡은 값이 68.1%다(§7). 낮아진 게 아니라 낙관 편향을
걷어낸 값이라고 봐야 한다.

> **남은 핵심 문제는 공유 쪽 seed가 1개라는 것이다.** 필기에서 배운 대로 **같은 설정에서
> seed만 바꿔도 평균 5.8%p, 최대 11.5%p** 흔들린다. §7의 차이(+2.2%p)는 그 폭 안에 있다.

### ⚠️ 정정 — 필기 단독 기준선은 있었다

초판에 *"필기 d64/L6 단독 기준선이 없다"* 고 썼으나 **틀렸다.** `SIZE_CONFIGS`의
`d64L6`(patch 100/50 · d64 · head 4 · L6 · d_ff 128)가 공유 모델과 **설정이 완전히
동일**하고, 결과가 seed 3개로 이미 있다.

| seed | 윈도우 | 피험자 hard | AUC | epoch |
|---|---|---|---|---|
| 42 | 0.7737 | 0.8051 | 0.8581 | 16.2 |
| 1 | 0.7793 | 0.8526 | 0.8633 | 13.0 |
| 7 | 0.7557 | 0.8218 | 0.8554 | 14.4 |
| **평균** | **0.769 ± 0.010** | **0.827 ± 0.020** | **0.859 ± 0.003** | 14.5 |

`results/` 안의 기존 파일을 확인하지 않고 단정한 실수다.

**다만 학습 조건이 두 가지 다르다** — 그래서 엄밀한 A/B는 아니다.

| | 단독 (`evaluate.py`) | 공유 (`train_shared.py`) |
|---|---|---|
| epoch / patience | 50 / 10 | **15 / 5** |
| 클래스 가중치 | 고정 2.0 / 1.0 | **역빈도 자동** |

단독이 평균 14.5 epoch까지 갔는데 공유 쪽은 상한이 15라 잘렸을 수 있다.
→ `train_shared.py --modalities hw`로 **같은 코드 경로에서 재실행**해야 조건이 맞는다.

또한 공정 비교를 위해 **단독 모델도 공유 모델과 같은 설정(d64/L6)으로 다시 돌려야** 한다.
필기 최적은 d64/L6, 음성 최적은 d128/L2로 서로 달라서, 그냥 비교하면 "공유 효과"와
"설정 효과"가 섞인다.

```
✅ 공유(d64 L6) vs 단독(d64 L6)      ← 설정 같음 → 공유 효과만 보임
❌ 공유(d64 L6) vs 단독(d128 L2)     ← 해석 불가
```

### 7-0. ⭐ 핵심 — 음성만 효과가 있고 필기는 없다

**3구성 × 3 seed = 9회 실행 완료** (필기 단독 / 음성 단독 / 2모달 공유 × seed 42·1·7).
집계: `python analyze_shared.py`

**ROC-AUC 기준** (피험자 정확도는 §7-3 참고 — 필기에서는 쓸 수 없다):

| | 단독 (seed 3) | 공유 (seed 3) | 차이 | t | 판정 |
|---|---|---|---|---|---|
| **음성** | 0.7333 | **0.7540** | **+0.0207** | **+3.96** | ✅ **효과 있음** |
| **필기** | 0.8543 | 0.8522 | −0.0021 | −0.21 | ✗ 효과 없음 |

음성은 **seed 3개 모두 양수**(+0.030 / +0.012 / +0.020)이고, 필기는 부호가 1+/2−로
엇갈리며 평균이 −0.002다.

### 판정 기준 셋 — 하나라도 걸리면 주장하지 않는다

| 기준 | 이유 |
|---|---|
| ① 부호 일관성 | seed 3개가 모두 같은 방향인가 |
| ② t ≥ 2 (seed 간) | 우연으로 보기 어려운가 |
| ③ **개선폭 > 공유 모델의 seed 변동폭** | 효과가 모델 자체의 흔들림보다 큰가 |

**③이 특히 중요하다.** 초판에서 *"단독 seed 노이즈가 0.001이니 +0.030은 30배"* 라고
썼는데 **잘못된 논거였다.** 비교 대상은 단독의 안정성이 아니라 **공유 모델 자체의
seed 변동폭**이다. 공유는 단독보다 불안정하다 — 두 모달의 기울기가 한 인코더로
들어오니 초기값에 더 민감하다.

6개 지표 중 **음성 AUC만 셋을 모두 통과**한다:

| 지표 | 부호 | t | 개선폭 vs 공유 변동폭 | |
|---|---|---|---|---|
| **음성 AUC** | 3/3 (+) | **+3.96** | 0.0207 > 0.0169 | ✅ |
| 음성 피험자 | 2+/1− | +1.19 | 0.0130 < 0.0380 | ✗ |
| 음성 윈도우 | 3/3 (+) | +1.57 | 0.0101 < 0.0308 | ✗ |
| 필기 AUC | 1+/2− | −0.21 | — | ✗ |
| 필기 피험자 | 2+/1− | +1.02 | 0.0338 < 0.0962 | ✗ |
| 필기 윈도우 | 1+/2− | −0.54 | — | ✗ |

### 해석 — 약한 모달만 얻어간다

```
음성 (AUC 0.733 · 235명 · 7,658 윈도우)   →  +0.021  효과 있음
필기 (AUC 0.854 ·  61명 · 13,474 윈도우)  →  −0.002  효과 없음
```

전이는 **잘 하는 쪽 → 못 하는 쪽**으로 흐른다. 필기는 이미 AUC 0.854로 충분히
학습돼 남에게 배울 것이 없고, 음성은 0.733이라 필기의 시계열 표현이 도움이 될
여지가 있었다.

> 이 비대칭 덕에 *"공유 인코더가 좋다"* 가 아니라 **"약한 모달이 강한 모달에서
> 얻어간다"** 는 더 구체적이고 반증 가능한 주장을 할 수 있다.

### 7-1. 음성 — 단독 vs 공유 인코더 (seed 3개)

같은 설정·같은 fold·같은 235명이라 **A/B 비교가 성립한다.**

| 지표 | 단독 평균 | 공유 평균 | 차이 | 부호 | t |
|---|---|---|---|---|---|
| **ROC-AUC** | 0.7333 | **0.7540** | **+0.0207** | **3/3 (+)** | **+3.96** |
| 화자 hard | 0.6768 | 0.6898 | +0.0130 | 2+/1− | +1.19 |
| 윈도우 정확도 | 0.6723 | 0.6824 | +0.0101 | 3/3 (+) | +1.57 |

seed별 AUC:

| seed | 단독 | 공유 | 차이 |
|---|---|---|---|
| 42 | 0.7317 | 0.7619 | +0.0302 |
| 1 | 0.7328 | 0.7450 | +0.0122 |
| 7 | 0.7354 | 0.7550 | +0.0196 |

**단독의 seed 변동폭이 0.0037로 매우 작다.** 화자가 235명이라 fold당 test ≈ 47명,
1명 ≈ 2.1%p로 필기(12명, 8.3%p)보다 4배 안정적인 것이 그대로 나타난다.
다만 판정 기준은 **공유 쪽 변동폭(0.0169)** 이고, 개선폭 0.0207이 그보다 크다.

### 7-2. ⚠️ 그래도 "지식 전이"라고 쓸 수 없다 — 원인을 못 가렸다

효과 자체는 §7-0의 세 기준을 통과했다. 남은 문제는 **그 효과가 무엇 때문인가**이다.

Notion 「2모달 Early Exit」 §3-1이 지적한 교란 셋 중 하나만 제거됐다.

| 교란 | 상태 |
|---|---|
| (a) 인코더 업데이트 횟수 2배 | ✅ 제거됨 — 손실 합산으로 스텝 수가 단독과 동일(부록 A-3) |
| **(b) 학습 데이터가 그냥 늘어남** | ❌ 남음 — 필기 13,474 윈도우가 추가로 인코더를 학습시킨다 |
| **(c) 이질 분포 혼합의 정규화 효과** | ❌ 남음 |

음성 AUC가 올랐어도 그것이 *"필기의 시계열 표현에서 배운 것"* 인지, 단순히
*"인코더가 더 많고 다양한 데이터를 봤기 때문"* 인지 구분되지 않는다.
가르려면 §3-1이 제시한 대조군이 필요하다.

| 대조군 | 확인하는 것 |
|---|---|
| 필기 대신 **가우시안 노이즈** 투입 | 그래도 오르면 (c) 정규화 효과 |
| 필기 **라벨을 셔플** | 그래도 오르면 (b) 또는 (c) |
| 필기를 **절반만** 사용 | 순수 데이터량 효과 측정 |

> **방어 가능한 진술**: *"음성 AUC가 공유 인코더에서 seed 3개 모두 높았다
> (+0.021, t=3.96). 필기는 효과가 없었다(−0.002). 다만 개선의 원인이 모달 간
> 지식 전이인지 데이터량·정규화 효과인지는 아직 가리지 못했다."*

#### fold 단위 paired t를 쓰지 않은 이유

seed 1개 안에서 fold별 차이로 paired t를 내면 t ≈ 2.77이 나온다(seed 42 기준).
그러나 **CV fold는 학습 데이터를 공유하므로 독립이 아니고**, 교차검증 결과에
paired t를 쓰면 1종 오류가 부풀려진다는 것은 알려진 문제다(Dietterich 1998).
그래서 여기서는 **seed를 표본 단위로 쓰는 t**만 보고한다(n=3, t=+3.96).

**이유 2 — 교란 두 개가 살아 있다.** Notion 「2모달 Early Exit」 §3-1이 지적한 셋 중,
손실 합산(부록 A-3) 덕에 (a) 인코더 업데이트 2배는 제거됐지만 나머지는 그대로다.

| 교란 | 상태 |
|---|---|
| 인코더 업데이트 횟수 | ✅ 제거됨 — 손실 합산으로 스텝 수가 단독과 동일 |
| **학습 데이터가 그냥 늘어남** | ❌ 남음 (필기 13,474 윈도우 추가) |
| **이질 분포 혼합의 정규화 효과** | ❌ 남음 |

AUC가 올랐어도 원인이 셋 중 무엇인지 구분되지 않는다. 가르려면 §3-1이 제시한
대조군(가우시안 노이즈 투입 / 라벨 셔플 / 필기 절반만)이 필요하다.

> **방어 가능한 진술**: *"seed 1개에서 5개 fold 중 4개가 같은 방향을 가리켰다.
> 방향은 고무적이나 판정 불가(t≈1.15)."*

### 7-3. 필기 — 공유 효과가 없다 (조건 일치 후)

`train_shared.py --modalities hw`로 **공유와 완전히 같은 조건**에서 seed 3개를 새로 돌렸다
(`results/ext_hw_s{42,1,7}.csv`). 이제 §5의 조건 불일치 문제가 없다.

**ROC-AUC** — 부호가 엇갈리고 평균이 −0.002다.

| seed | 단독 | 공유 | 차이 |
|---|---|---|---|
| 42 | 0.8467 | 0.8632 | +0.0165 |
| 1 | 0.8646 | 0.8464 | **−0.0182** |
| 7 | 0.8517 | 0.8470 | −0.0047 |
| **평균** | **0.8543** | **0.8522** | **−0.0021** (t = −0.21) |

**공유해서 얻은 것도 잃은 것도 없다.**

### ⚠️ 피험자 정확도의 "+9.75%p"는 seed 하나짜리 착시다

seed 42만 보면 0.804 → 0.901로 **+9.75%p**다. 그런데 seed를 늘리면:

| seed | 단독 | 공유 | 차이 |
|---|---|---|---|
| 42 | 0.8038 | 0.9013 | **+0.0975** |
| 1 | 0.8679 | 0.8538 | −0.0141 |
| 7 | 0.7872 | 0.8051 | +0.0179 |
| **평균** | 0.8196 | 0.8534 | +0.0338 (t = +1.02) |

**공유 쪽 seed 변동폭이 0.0962로 평균 개선폭(0.0338)의 3배**다. 판정 불가다.

원인은 표본 크기다 — fold당 test가 12명이라 **1명 = 8.3%p**. 공유 seed 42의
fold별 값이 0.917 / 0.750 / 0.923 / 0.917 / **1.000**(12명 전원)인데,
이 정도 요동은 3명 차이에 불과하다.

> `depth_ee_findings.md` §2-6이 *"피험자 단위 정확도를 지표로 쓸 수 없다 — 시드 간
> 표준편차 ±4.1%p, 일부 설정은 ±6.0%p"* 라고 한 그 문제다. **필기에서는 AUC만 봐야
> 한다.** 음성은 화자 235명·fold당 47명이라 상대적으로 쓸 만하다(변동폭 0.0079).

이 절은 초판에서 *"필기 단독 대비 +7.4%p 개선"* 으로 썼던 것을 **정정한 것**이다.
seed 1개로 본 개선이 seed 노이즈와 구분되지 않았다.

> README §5-1: *"`p50` 설정은 seed 42에서 91.7%가 나왔지만 seed 7에서는 80.4%였다.
> 처음 91.7%만 보고 결론냈다면 재현되지 않았을 것이다."* — 이번 fold 1이 정확히
> 그 91.7%(12명 중 11명)다.

### 7-4. 부수 관찰

- **조기중단이 매우 이르다.** best epoch가 음성 단독 1~7(평균 8.2 epoch에서 종료),
  2모달 3~8(평균 9.8). 6층이 이 과제에 과하다는 신호이며,
  `depth_ee_findings.md`의 "깊이는 무용하다"와 방향이 같다.
- **필기 단독을 `train_shared.py`로 돌린 값이 `evaluate.py` 값보다 낮다.**
  피험자 0.820 vs 0.827, AUC 0.855 vs 0.859로 근소하나 일관되게 낮다.
  epoch 상한(15 vs 50)과 클래스 가중치(자동 vs 고정 2.0/1.0) 차이로 보인다.
  단독이 평균 14.5 epoch까지 갔으므로 **상한 15는 빠듯하다** — 비교에는 지장이 없으나
  (공유도 같은 상한) 절대값을 다른 문서와 대조할 때는 주의해야 한다.
- **CPU로는 실험을 못 돌린다.** 음성이 80채널이라 배치당 `64×80 = 5,120` 시퀀스가
  인코더를 통과한다(필기는 384). 스텝당 4.2초 × 152스텝 × 5-fold = 10시간.
  같은 작업이 RTX 5050이면 15~20분으로 추정된다.

| 2모달 공유 | 152 | ~4.2초 | 8~10시간 |

음성이 무거운 이유는 채널 수다 — channel-independent 패칭이라 배치 64에 대해
필기는 `64×6=384` 시퀀스, 음성은 `64×80=5,120` 시퀀스가 인코더를 통과한다.

**seed 3개를 채우는 데 CPU로 약 40시간이 들었다.** GPU(RTX 5050)면 같은 9회가
2~3시간으로 추정되므로, 이후 실험은 GPU로 옮기는 것이 맞다.

> Early Exit은 여전히 붙이지 않았다. 깊이 축은 `depth_ee_findings.md`에서 작동하지
> 않음이 확정됐고(정적 L1 ≈ L6, t=0.51), §7-4의 조기중단 관찰(best epoch 1~8)도
> 같은 방향이다. 현재 우선순위는 시간 축(`paper/exp2_protocol.md`)이다.

# 부록. 무엇을 왜 이렇게 고쳤나

> 이번 작업에서 내린 결정과 그 근거. 특히 **한 번 틀렸다가 고친 것**은 과정을 남긴다.
> 결과만 적으면 "왜 그 방식이냐"는 질문에 다시 답할 수 없기 때문이다.

## A-1. 병합 키를 `번호` → `(클래스, 번호)` 로 고침 ⭐

**처음 한 것** — 원본 파일명 맨 뒤 숫자만으로 사람을 식별해 data4를 data3에 합쳤다.
정렬 대응 검산(파일 수·라벨)이 111/111, 101/101로 전부 통과해서 맞다고 봤다.

**증상** — 사후 검증에서 라벨 충돌 2건이 떴다.

```
정정 후 실제 사람  : 233명
한 사람이 두 라벨을 갖는 경우: 2건 ❌ [143, 144]
→ 라벨 충돌. 매핑이 틀렸다는 뜻이므로 저장하지 않는다.
```

**원인** — `전처리_audio`의 **HC 68**과 `전처리_pataka`의 **PD 68**을 한 사람으로 합쳤다.
번호는 코퍼스 전역이 아니라 **클래스 안에서만 유일**하다. README가 HC 명단과 PD 명단을
따로 나열한 것이 그 뜻이었는데, 번호만 보고 놓쳤다.

정렬 검산이 통과한 이유도 이걸로 설명된다 — 각 수집분 **안에서는** 번호가 클래스에 걸쳐
겹치지 않아(111명 중 0건) 번호 오름차순이 사람을 유일하게 정한다. 문제는 수집분을
**가로질러** 합칠 때만 드러난다.

**고친 것** — 사람 키를 `(클래스, 번호)` 쌍으로 바꿨다. 병합 대상이 101 → **99명**으로 줄고
라벨 충돌이 0건이 됐다. 아울러 "이 수집분 안에서 번호가 HC·PD에 겹치는가"를 먼저 확인하는
가드를 넣어, 정렬 가설이 성립하지 않는 데이터가 들어오면 즉시 멈추게 했다.

**남긴 교훈** — 이 오류를 잡은 건 사후 검증(라벨 충돌 검사)이었다. 그게 없었으면 잘못된
매핑이 그대로 저장되고, 두 사람이 한 사람으로 합쳐진 채 fold가 갈렸을 것이다.
**"검산이 어긋나면 저장하지 않는다"는 가드를 먼저 짜고 매핑을 만든 것이 유효했다.**

## A-2. 데이터 파일을 고치지 않고 매핑표만 내보낸 이유

| | npz 직접 수정 | **매핑표(JSON) 방식** |
|---|---|---|
| 되돌리기 | 어려움 (1,658개 재생성) | 파일 하나 지우면 끝 |
| 리뷰 | 바이너리 diff | 텍스트 diff |
| 원본 fidelity | 훼손 | 유지 |
| 68·69 결론 바뀌면 | 전체 재변환 | **두 줄 수정** |

아직 확정 안 된 질문(68·69)이 남아 있는 상태에서 원본을 덮어쓰는 건 이르다고 봤다.
윈도잉 단계에서 `canonical_subject_id()`로 적용하면 결과는 같으면서 되돌릴 수 있다.

## A-3. 두 모달 손실을 합산해 backward를 **한 번만** 호출

**문제** — Notion 「2모달 Early Exit」 §3-1이 지적한 교란 셋 중 하나가
*"인코더 업데이트 횟수 약 2배(배치를 번갈아 돌림)"* 였다. 공유 모델이 더 좋게 나와도
그게 지식 전이 때문인지 그냥 더 많이 업데이트해서인지 구분되지 않는다.

**고친 것** — 모달을 번갈아 backward 하지 않고 한 스텝에서 두 손실을 **합산한 뒤
backward를 한 번만** 호출한다.

```python
loss = criteria["hw"](model(x_hw, "hw"), y_hw) \
     + criteria["voice"](model(x_voice, "voice"), y_voice)
loss.backward()      # 두 기울기가 같은 인코더로 함께 흘러들어감
optimizer.step()     # 스텝은 1회
```

**결과** — epoch당 옵티마이저 스텝 수가 필기 단독 학습과 **같아진다**(둘 다 152스텝).
교란 3개 중 하나가 구조적으로 제거됐다. 남은 둘(데이터량 증가, 이질 분포 혼합)은 여전히
대조군이 필요하다.

## A-4. 로더 길이 불일치 — `longest` 를 기본으로

필기 13,474 vs 음성 2,008 윈도우로 6.7배 차이가 난다.

| | zip (shortest) | **longest (기본)** |
|---|---|---|
| 필기 데이터 | 매 epoch **85% 버림** | 전부 사용 |
| 음성 데이터 | 전부 사용 | 약 6.7회 반복 노출 |
| 단독 기준선과 비교 | **깨짐** (학습 데이터가 다름) | 성립 |

필기 85%를 버리면 "공유 vs 단독" 비교에서 학습 데이터량이 달라져 §5의 공정 비교 조건이
무너진다. 그래서 `longest`를 골랐다. 대가는 음성 과적합이 빨라지는 것이고,
`--pair-mode shortest`로 바꿔 확인할 수 있게 남겼다.

## A-5. 위치 인코딩을 sinusoidal로 유지 (설계 문서와 다름)

설계 문서의 파라미터 수치(모달 전용 13,580 / 51,340)는 **학습형 PE**를 가정한 것으로 보인다.
그래도 `model.py`와 동일한 **sinusoidal**(파라미터 0)을 유지했다.

**이유** — 이 모델의 존재 이유가 "같은 설정 단독 모델과 비교해 공유 효과만 분리하는 것"이다.
백본 구성이 하나라도 다르면 §5에서 지적한 것처럼 "공유 탓인지 설정 탓인지" 섞인다.
`model.py`의 `PatchTSTClassifier`와 RevIN·PE·pre-LN·GELU·channel-independent 패칭을
전부 일치시키는 쪽을 택했다.

**부수 효과** — 공유 비율이 문서(75.6%)보다 높은 **92.1%**가 됐다. "인코더를 공유했다"는
주장에는 유리하지만, 문서 수치와 어긋나므로 §6에 확인 사항으로 남겼다.

## A-6. 조기중단을 모달 val loss의 **합**으로

인코더가 하나뿐이라 모달별로 다른 시점에 멈출 수가 없다. 합으로 걸면 한 모달이 먼저
과적합해도 다른 쪽이 내려가는 동안 합이 계속 줄어 멈추지 않는다.

**구조적 타협임을 인정하고**, 대신 모달별 val loss를 따로 기록해 눈으로 확인할 수 있게 했다.
"공유 모델은 조기중단 시점이 단독과 다를 수 있다"는 점은 §5 비교에서 감안해야 한다.

## A-7. 모달별 클래스 가중치를 따로 계산

필기(1:1.77)와 음성(1:1.04)은 불균형 정도가 다르다. 한쪽 비율로 양쪽을 덮으면 다른 모달의
손실이 왜곡되므로, fold별 train 분포에서 각각 역빈도로 계산한다.
분모에 클래스 수를 두어 가중치 평균이 1.0이 되게 했다 — 손실 스케일이 유지되어
learning rate를 다시 잡을 필요가 없다.

## A-8. 검증 범위를 정직하게 표기

torch를 못 돌리는 환경이라 "학습이 돌아간다"를 확인할 수 없었다. 그래서 확인한 것과
못 한 것을 §3에 나눠 적었고, 커밋 메시지에도 남겼다. 돌려보지 않은 코드를
"동작 확인됨"으로 적으면 나중에 그 표기를 믿고 넘어가게 된다.

numpy로 검산 가능한 부분(텐서 shape 수식, 파라미터 수)은 실제로 재현해서 확인했고,
공유 인코더 파라미터가 설계 문서의 200,832와 소수점까지 일치하는 것까지는 확인했다.
